# POST.md

## Blog Post Rules

Blog posts live in:

```text
src/content/blog/
```

Each post should be created as a Markdown or MDX file:

```text
src/content/blog/my-post-slug.md
src/content/blog/my-post-slug.mdx
```

Use lowercase slugs with hyphens. The filename becomes the route:

```text
src/content/blog/my-post-slug.md -> /blog/my-post-slug/
```

## Required Frontmatter

Every blog post must include:

- `title`: public post title.
- `description`: short summary used in indexes, metadata, RSS, and previews.
- `pubDate`: publication date.

Optional fields:

- `seoTitle`: longer search and social title used in page metadata.
- `updatedDate`: last meaningful update date.
- `heroImage`: local promotional image imported through frontmatter.
- `tags`: searchable topic labels used for metadata and blog navigation.

The current schema is defined in `src/content.config.ts`.

## Promotional Image

Use `heroImage` when the post needs a visual preview or Open Graph image.

`heroImage` is also used as the social sharing thumbnail through the Open Graph and Twitter metadata generated by `BaseHead.astro`. If a post does not define `heroImage`, the site falls back to the default image configured in `BaseHead.astro`.

Images should be grouped by the post they belong to. Use the post slug as the folder name:

```text
src/content/blog/my-post-slug.md
src/assets/blog/my-post-slug/
```

The promotional image should live inside that folder and use a predictable name:

```text
src/assets/blog/my-post-slug/hero.jpg
src/assets/blog/my-post-slug/hero.png
src/assets/blog/my-post-slug/hero.webp
```

Frontmatter example:

```yaml
heroImage: '../../assets/blog/my-post-slug/hero.png'
```

Image guidance:

- Use a relevant image that supports the post topic.
- Use an image that can work as a social media preview thumbnail.
- Keep images web-friendly and optimized.
- Prefer local project assets over remote image URLs.
- Keep post-specific images inside `src/assets/blog/{post-slug}/`.
- Do not store post-specific images directly under `src/assets/`.
- Use shared images only when the image is intentionally reused across multiple posts.
- Name internal images by purpose, such as `data-flow.png`, `query-plan.webp`, or `validation-output.jpg`.
- The image folder name must match the post slug.
- If the post is technical, the image should help explain the idea or give useful context.

Social platforms can cache link previews. If `heroImage`, `title`, or `description` changes after a link has already been shared, the platform may need time or a manual re-scrape/debug action before showing the updated preview.

Example aligned structure:

```text
src/content/blog/databricks-validation-harness.md
src/assets/blog/databricks-validation-harness/hero.webp
src/assets/blog/databricks-validation-harness/data-flow.png
src/assets/blog/databricks-validation-harness/validation-output.png
```

## Content Requirements

A publishable post should have:

- A clear introduction that explains the problem, idea, or context.
- Structured headings using `##` and `###`.
- Enough detail to be useful without becoming noisy.
- Concrete examples when explaining engineering decisions.
- Links to sources, docs, repositories, or references when needed.
- A concise closing section or takeaway.

Content can include a mix of:

- Markdown prose.
- Lists.
- Code blocks.
- Images.
- Tables.
- Links.
- MDX components, only when the post needs richer rendering.

Keep the content in English unless the post is intentionally written for a Spanish-speaking audience.

## Engineering Notes

When writing technical posts, prefer an engineering-oriented structure:

- Context: what problem or system is being discussed.
- Constraints: what mattered for the decision.
- Approach: how the solution works.
- Tradeoffs: what was accepted or avoided.
- Validation: how the result was checked.
- Takeaways: what should be remembered.

For backend, data, SQL, Python, Databricks, or harness topics, be specific about contracts, data flow, validation boundaries, and failure modes.

## Pre-Publish Checklist

Before publishing a post:

- Confirm the file is inside `src/content/blog/`.
- Confirm the slug is lowercase and hyphenated.
- Confirm post-specific images are inside `src/assets/blog/{post-slug}/`.
- Confirm the image folder name matches the post slug.
- Confirm required frontmatter is present.
- Confirm dates are valid and intentional.
- Confirm `title` is concise enough for the UI.
- Confirm `seoTitle`, when present, includes useful search keywords without making the visible title too long.
- Confirm `description` is useful for previews and metadata.
- Confirm `heroImage` exists if provided and points to the matching post image folder.
- Confirm `heroImage` is suitable for social sharing previews.
- Confirm `tags` are specific, accurate, and not overloaded.
- Confirm all images in the post folder are referenced by the post, or are intentionally reserved for that post.
- Confirm the post does not reference another post's image folder unless the reuse is intentional.
- Confirm headings are structured and readable.
- Confirm links work.
- Run the build:

```sh
npm run build
```

The build should pass before merging or deploying.
