# PROJECT.md

## Project Writeup Rules

Project writeups live in:

```text
src/content/projects/
```

Each project should be created as a Markdown or MDX file:

```text
src/content/projects/my-project-slug.md
src/content/projects/my-project-slug.mdx
```

Use lowercase slugs with hyphens. The filename becomes the route:

```text
src/content/projects/my-project-slug.md -> /projects/my-project-slug/
```

## Required Frontmatter

Every project writeup must include:

- `title`: public project title.
- `description`: short project summary used in indexes, metadata, and previews.
- `promoImage`: local promotional image for the project detail page and metadata.
- `githubUrl`: public repository or relevant GitHub profile URL.

Optional fields:

- `pubDate`: publication or project date.
- `stack`: list of tools, languages, frameworks, or platforms used.

The current schema is defined in `src/content.config.ts`.

## Project Images

Project images should be grouped by the project they belong to. Use the project slug as the folder name:

`promoImage` is also used as the social sharing thumbnail through the Open Graph and Twitter metadata generated by `BaseHead.astro`.

```text
src/content/projects/my-project-slug.md
src/assets/projects/my-project-slug/
```

The promotional image should live inside that folder and use a predictable name:

```text
src/assets/projects/my-project-slug/promo.jpg
src/assets/projects/my-project-slug/promo.png
src/assets/projects/my-project-slug/promo.webp
```

Frontmatter example:

```yaml
promoImage: '../../assets/projects/my-project-slug/promo.webp'
```

Image guidance:

- Use a relevant image that shows the actual project, product state, architecture, workflow, or result.
- Use an image that can work as a social media preview thumbnail.
- Keep images web-friendly and optimized.
- Prefer local project assets over remote image URLs.
- Keep project-specific images inside `src/assets/projects/{project-slug}/`.
- Do not store project-specific images directly under `src/assets/`.
- Use shared images only when the image is intentionally reused across multiple projects.
- Name internal images by purpose, such as `architecture.png`, `dashboard.webp`, `pipeline-flow.png`, or `mobile-screen.jpg`.
- The image folder name must match the project slug.

Social platforms can cache link previews. If `promoImage`, `title`, or `description` changes after a link has already been shared, the platform may need time or a manual re-scrape/debug action before showing the updated preview.

Example aligned structure:

```text
src/content/projects/databricks-quality-harness.md
src/assets/projects/databricks-quality-harness/promo.webp
src/assets/projects/databricks-quality-harness/architecture.png
src/assets/projects/databricks-quality-harness/validation-report.png
```

## Content Requirements

A publishable project writeup should have:

- A clear summary of what the project does.
- Context about the problem, audience, or use case.
- Technical decisions and tradeoffs.
- Architecture, data flow, or workflow explanation when relevant.
- Validation strategy, testing approach, or operational notes.
- Links to repository, docs, demos, or references when available.
- A concise closing section with results or takeaways.

Content can include a mix of:

- Markdown prose.
- Lists.
- Code blocks.
- Images.
- Tables.
- Links.
- MDX components, only when the project needs richer rendering.

Keep the content in English unless the project writeup is intentionally written for a Spanish-speaking audience.

## Engineering Notes

When writing technical project pages, prefer a backend and data engineering lens:

- Context: what problem the project solves.
- Contract: inputs, outputs, APIs, schemas, or content expectations.
- Architecture: components, boundaries, and integration points.
- Data flow: where data comes from, how it is transformed, and where it goes.
- Validation: tests, harnesses, checks, monitoring, or manual QA.
- Tradeoffs: what was optimized, deferred, or intentionally avoided.
- Operations: build, deploy, runtime, and failure considerations.

For SQL, Python, Databricks, backend, or harness projects, be explicit about reproducibility, data quality, observability, and failure modes.

## Pre-Publish Checklist

Before publishing a project:

- Confirm the file is inside `src/content/projects/`.
- Confirm the slug is lowercase and hyphenated.
- Confirm project-specific images are inside `src/assets/projects/{project-slug}/`.
- Confirm the image folder name matches the project slug.
- Confirm required frontmatter is present.
- Confirm `githubUrl` is valid and intentional.
- Confirm `description` is useful for previews and metadata.
- Confirm `promoImage` exists and points to the matching project image folder.
- Confirm `promoImage` is suitable for social sharing previews.
- Confirm all images in the project folder are referenced by the project, or are intentionally reserved for that project.
- Confirm the project does not reference another project's image folder unless the reuse is intentional.
- Confirm `stack` values are accurate and useful for the project index.
- Confirm headings are structured and readable.
- Confirm links work.
- Run the build:

```sh
npm run build
```

The build should pass before merging or deploying.
